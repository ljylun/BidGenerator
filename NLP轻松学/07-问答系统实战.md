## 开篇除恐

这一章的主题是 **Question Answering（问答系统）**。

听到"问答系统"，很多人会想到科幻电影里的 AI："你好，我是贾维斯。" 但现实中的 QA 系统没那么玄。它不会跟你聊哲学，它的任务是：**你给一段文章，再给一个问题，它从文章里找出答案。**

它不是在"理解"你，它是在"找"答案。

你怕的不是 QA 难，是觉得它需要某种神秘技术。这一章告诉你：它就是一个**管道（Pipeline）**，由几个普通零件拼起来。

---

## 白话化

先拆三个核心词：

| 术语 | 大白话 | 画面 |
|------|--------|------|
| **Retriever（检索器）** | 图书管理员 | 你问一个问题，它在几万本书里先缩小范围，找出可能相关的几页 |
| **Reader（阅读器）** | 仔细看那几页的人 | 真的去读那几页，把答案片段摘出来 |
| **Pipeline（管道）** | 流水线 | 问题先过检索器，再进阅读器，最后输出答案 |

**规矩**：基于 Transformer 的 QA 系统通常走**抽取式（extractive）**路线——不是自己编答案，而是从原文里"抠"出一段作为答案。

---

## 直觉先行

先手动做一遍 QA，你就懂机器在干什么了。

**任务**：给一段评论文本，回答 "这家酒店早餐怎么样？"

**原文（人工节选，简化）**：
> "这家酒店位置很棒，就在地铁口。房间干净整洁，就是有点小。早餐品种挺丰富，中西式都有，但咖啡不太好喝。前台服务很热情。"

**你的做法**：
1. 看到问题 "早餐怎么样"，脑子里先找"早餐"相关句子。
2. 锁定："早餐品种挺丰富，中西式都有，但咖啡不太好喝。"
3. 摘出答案片段："早餐品种挺丰富，中西式都有，但咖啡不太好喝。"

**机器做的事完全一样**：
1. **Retriever**：在海量评论文档里，找出最可能包含答案的那几篇。
2. **Reader**：真正去读那几篇，把答案片段抽出来。

你不需要懂 Transformer 内部细节，就能看懂这个流程。

## 例子贴身

### 例子 1：用 Haystack 搭一个最小 QA Pipeline（☼☼）

**Haystack** 是一个帮你搭 QA 系统的框架，你不用从零写检索和阅读逻辑。

**场景**：基于酒店评论的问答系统。

**第一步：准备文档**

把每条评论当作一个独立文档：

```
文档 1："这家酒店位置很棒，就在地铁口。房间干净整洁，就是有点小。早餐品种挺丰富，中西式都有，但咖啡不太好喝。前台服务很热情。"
文档 2："酒店在海边，风景无敌。不过隔音很差，晚上能听到隔壁说话。性价比一般。"
...
```

**第二步：建索引（Indexing）**

用 Retriever 把这些文档变成"可搜索"的格式。简单说，就是把文档转化成向量，存在一个专门的数据库里。

```python
# 概念代码，示意用
from haystack.document_stores import InMemoryDocumentStore
from haystack.nodes import Retriever, Reader
from haystack.pipelines import ExtractiveQAPipeline

# 1. 建一个内存数据库
document_store = InMemoryDocumentStore()

# 2. 把评论写进去
document_store.write_documents([
    {"content": "早餐品种挺丰富，中西式都有，但咖啡不太好喝。", "meta": {"source": "review_1"}},
    # ... 更多评论
])

# 3. 用 Retriever 建索引
retriever = Retriever(document_store=document_store)

# 4. 用 Reader 读内容（基于预训练模型）
reader = Reader(model_name_or_path="deepset/roberta-base-squad2")

# 5. 组装 Pipeline
pipe = ExtractiveQAPipeline(reader, retriever)
```

**第三步：问问题**

```python
# 问一个关于早餐的问题
result = pipe.run(
    query="这家酒店早餐怎么样？",
    params={"Retriever": {"top_k": 3}, "Reader": {"top_k": 1}}
)

print(result["answers"][0].answer)
# 可能输出："品种挺丰富，中西式都有，但咖啡不太好喝"
```

**你看到了什么？**
- 你只写了 5 步，一个能工作的 QA 系统就跑起来了。
- Retriever 负责"找相关段落"。
- Reader 负责"从段落里抠答案"。

**原书** 里用的就是这个路线，数据是酒店评论数据集（Hugging Face 上的 `jamescalam/hotpot_qa` 变体，或其他）。

### 例子 2：评估你的 QA 系统（☼）

光能跑还不够，你得知道它好不好用。原书介绍了两种评估方式：

**评估 Retriever（找得准不准）**
- 给一组问题，看 Retriever 能不能把含答案的文档排在前面。
- 指标：**Hit Rate**（前 k 个结果里有没有命中）、**MRR**（平均 reciprocal rank）。

**评估 Reader（读得准不准）**
- 给已知答案的问题，看 Reader 能不能精确抠出答案。
- 指标：**Exact Match (EM)**（抠出来的答案跟标准答案一模一样）、**F1**（抠出来的答案跟标准答案有多少词重合）。

**自编例子**：假设我们有 10 个问题。

| 问题 | 标准答案 | 系统输出 | 是否命中 |
|------|---------|---------|---------|
| 早餐怎么样？ | 品种挺丰富，中西式都有 | 品种挺丰富，中西式都有 | ✓ |
| 咖啡好喝吗？ | 咖啡不太好喝 | 咖啡不太好喝 | ✓ |
| 房间大吗？ | 有点小 | 房间很大 | ✗ |

- **EM = 2/3**（3 题里 2 题完全对）
- **F1**：第 3 题虽然错了，但"房间"和"小"都对，F1 可能是 0.5 左右。

**原书** 给出的评估方法就是这个逻辑，没有更复杂的数学。

### 例子 3：让 QA 系统更聪明（☼）

原书第 7 章后半段讲了几种改进方式，挑重点说：

**1. 换个更大的 Reader**
- 小模型可能抠不准，换 BERT-large 或 RoBERTa-large。
- 代价：跑得慢，吃内存。

**2. 调整 Retriever 的 top_k**
- `top_k=3` 表示只拿最相关的 3 篇给 Reader。
- 太小可能漏答案，太大可能塞进无关内容，让 Reader 分心。

**3. 领域适应（Domain Adaptation）**
- 通用模型在法律、医疗、酒店评论上表现可能一般。
- 办法：用你自己领域的文本再训练（fine-tune）一下。

**自编比喻**：Retriever 是"缩小搜索范围"，Reader 是"仔细看"。你想让系统更准，要么让检索更准（别给无关内容），要么让阅读更准（模型更大/更专）。

## 这一章要带走的东西

- QA 系统不是让机器"懂"问题，是让机器**会找答案**。
- **Retriever + Reader + Pipeline** 是标准三段式。
- Haystack 框架把这三段封装好了，几行代码就能跑。
- 评估看两个维度：Retriever 找得准不准，Reader 读得准不准。
