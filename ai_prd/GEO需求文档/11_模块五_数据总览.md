## 11.4 错误处理规范

| 错误场景 | 触发条件 | 系统处理 | 用户提示 | 恢复策略 |
|----------|----------|----------|----------|----------|
| 数据同步延迟 | 平台 API 数据更新延迟 >5 分钟 | 展示最近一次成功同步的时间戳，标记数据为"延迟"状态 | ⚠️ 数据已延迟 XX 分钟，正在同步中... | 自动每 30 秒重试同步，成功后刷新页面 |
| 数据异常波动 | 关键指标波动超过 ±30%（环比） | 标记异常数据点，触发后台数据校验 | ⚠️ 检测到 XX 指标异常波动，已通知管理员 | 后台自动校验数据源，排除 API 异常后更新 |

### 11.5.2 ROI 归因模型详细说明

系统提供四种归因模型，用户可根据业务场景切换：

#### 模型一：首次归因（First-Touch Attribution）

- **原理**：将 100% 的转化功劳归于用户第一次接触的渠道/策略
- **适用场景**：评估拉新能力、渠道获客效果
- **计算公式**：`功劳(首次触点) = 100%，其余触点 = 0%`
- **示例**：用户首次通过 ChatGPT 搜索发现品牌 → ChatGPT 渠道获得全部转化功劳

#### 模型二：末次归因（Last-Touch Attribution）

- **原理**：将 100% 的转化功劳归于转化前最后一次触点
- **适用场景**：评估最终转化推动力、短期效果评估
- **计算公式**：`功劳(末次触点) = 100%，其余触点 = 0%`
- **示例**：用户最终通过 Gemini 引用完成转化 → Gemini 渠道获得全部转化功劳

#### 模型三：线性归因（Linear Attribution）

- **原理**：所有触点平均分配转化功劳
- **适用场景**：评估全链路贡献、均衡分析
- **计算公式**：`功劳(每个触点) = 100% / 触点总数`
- **示例**：用户经过 4 个触点 → 每个触点获得 25% 的转化功劳

#### 模型四：时间衰减归因（Time-Decay Attribution）

- **原理**：离转化越近的触点获得越高的功劳权重
- **适用场景**：长周期决策场景、持续性运营评估
- **计算公式**：`功劳(触点i) = (t_i - t_min) / Σ(t_j - t_min)`，其中 `t_i` 为触点时间，`t_min` 为最早触点时间
- **示例**：转化前 1 天的触点权重高于转化前 30 天的触点

**归因模型配置表**：

| 属性 | 首次归因 | 末次归因 | 线性归因 | 时间衰减归因 |
|------|----------|----------|----------|-------------|
| 默认启用 | 否 | 否 | **是** | 否 |
| 最大触点数 | 无限制 | 无限制 | 无限制 | 建议 ≤10 |
| 回溯窗口 | 30 天 | 30 天 | 30 天 | 90 天 |
| 计算复杂度 | O(1) | O(1) | O(n) | O(n) |
| 实时性 | 实时 | 实时 | 近实时(T+1) | 近实时(T+1) |

### 11.5.4 强化学习优化闭环原理

```
┌─────────────────────────────────────────────────────────┐
│                 强化学习优化闭环                          │
│                                                         │
│    ┌──────────┐                          ┌──────────┐   │
│    │  AI 平台  │◀────── 策略执行 ────────│  策略代理  │   │
│    │ (环境)    │                          │ (Agent)  │   │
│    └────┬─────┘                          └────▲─────┘   │
│         │                                     │         │
│         ▼                                     │         │
│    ┌──────────┐     ┌──────────┐     ┌──────────┐      │
│    │ 状态观测  │────▶│ 奖励计算  │────▶│ 策略更新  │      │
│    │ (State)  │     │ (Reward) │     │ (Update) │      │
│    └──────────┘     └──────────┘     └──────────┘      │
│                                                         │
│  状态空间: [曝光量, 引用率, 转化率, 内容质量分,          │
│            关键词覆盖度, 竞品对比度, ...]                │
│                                                         │
│  动作空间: [内容发布频率, 关键词调整, 渠道配比,          │
│            品牌信号强度, 外链策略, ...]                  │
│                                                         │
│  奖励函数: R = w1×Δ曝光 + w2×Δ引用率 +                │
│                w3×Δ转化率 - w4×成本                     │
│                                                         │
│  算法: PPO (Proximal Policy Optimization)               │
└─────────────────────────────────────────────────────────┘
```

**强化学习闭环运行流程**：

1. **状态观测**：每 4 小时从各 AI 平台采集最新 GEO 指标作为当前状态
2. **策略决策**：Agent 根据当前状态选择最优动作（策略调整方案）
3. **策略执行**：将策略调整方案推送给对应执行模块（内容管理、关键词优化等）
4. **奖励计算**：策略执行后 24 小时，计算奖励值（综合指标变化）
5. **策略更新**：基于奖励值更新策略网络参数，优化下次决策

### 11.5.5 数据聚合和缓存策略

| 数据类型 | 聚合粒度 | 更新频率 | 缓存策略 | 保留周期 |
|----------|----------|----------|----------|----------|
| 曝光量指标 | 小时级 | 实时（Flink） | Redis，TTL 5 分钟 | 2 年 |
| 引用率指标 | 天级 | T+1（ETL） | Redis，TTL 1 小时 | 2 年 |
| 转化数据 | 天级 | T+1（ETL） | Redis，TTL 1 小时 | 3 年 |
| 归因分析结果 | 周级 | 手动/定时 | 本地缓存，TTL 24 小时 | 1 年 |
| 策略推荐结果 | 天级 | 每日 8:00 | Redis，TTL 6 小时 | 30 天 |
| 看板配置 | 实时 | 变更触发 | 本地存储 + 服务端持久化 | 永久 |
